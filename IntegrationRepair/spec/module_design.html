Integration repair / implemented architecture

Compare pages.
Persist only upserts.

One Oracle reader fetches the next 10,000-row page while the main thread looks up the current page's keys in LIFT, compares dates, and saves only missing or outdated records in SQLite.

The sequence

Prepare

  1. Create run and capture the cutoff; count eligible LIFT rows.
  2. Receive an Oracle page and request exactly one page ahead.
  3. Count its eligible rows; look up its keys in LIFT within the cutoff.
  4. Compare, warn on ahead records, save only insert/update differences.
  5. At end of stream, save counts and mark preparation finished.

Apply

  1. Read a pending upsert page and fetch its source payloads.
  2. Recheck prepared pairs; map valid payloads.
  3. Commit PostgreSQL upserts, then save SQLite outcomes.
  4. Fill point sampling fields and finish; leave materialized views untouched.
Prepare → Review run counts and upsert_diff → Apply

Visibility into each table

Each run stores its creation time, table name, cutoff, Oracle/LIFT counts, and planned insert/update counts. Both populations use change_time ≤ cutoff. The Oracle count comes from the integration query's eligible result.

expected_needed_deletions = lift_count + insert_count - oracle_count

A signed diagnostic estimate: negative values are saved and warned about. It assumes planned inserts succeed. Updates do not change row counts; actual writes can differ when apply skips changed source rows. LIFT-only rows and materialized views are left untouched.

Small storage, bounded memory

SQLite contains only integration_transfer and upsert_diff. One current source page, one fetched-ahead page, and current comparison data stay in memory. All source key/date pairs still cross the network; full payloads are fetched only for pending upserts.
