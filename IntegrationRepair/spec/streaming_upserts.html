Proposal for agreement · Python implementation unchanged

Compare each page.
Save only the upsert differences.

Prepare becomes a source-driven loop: fetch 10,000 Oracle key/date pairs, look up those keys in LIFT, and save only missing or older rows to SQLite. While we compare the current page, one background reader fetches the next page.

What gets smaller: SQLite storage and writes. Current RAM use is already page-bounded; it does not hold the entire inventory in memory. We still transfer every source key/date pair to compare it. Full payloads are fetched only for saved upserts during apply.

The new sequence

Oracle reader · page N + 1

One worker owns the inventory cursor and fetches the next page. Only one fetch can be outstanding; it waits once that page is ready.

Main thread · page N

One PostgreSQL lookup for the page’s keys → compare dates → commit the upsert differences and warning count to SQLite → discard the page.

Repeat → Finish preparation → Review SQLite → Apply upserts → Completion work

Use one ThreadPoolExecutor(max_workers=1) and one future. PostgreSQL and SQLite stay on the main thread. There is no async framework, worker pool, or unbounded queue.

Deletion is off, without a cleanup rewrite

Keep the existing deletion functions and tables. New runs leave remote_ids_and_date_changed and removal_diff empty and report delete_count = 0. No dummy rows are needed. LIFT-only keys are never visited, so the three extra test rows will remain.

Start a fresh prepared run for this mode. Old runs keep their historical differences; disabling deletion must also stop old saved removals from being executed. Use a fresh SQLite file, such as ev-upserts.sqlite, to see the storage reduction: existing inventory data does not disappear or shrink automatically.

Short prepare pseudocode 
run = store.create_run(integration_id, cutoff, table_name)
pages = source.inventory(cutoff)

with ThreadPoolExecutor(max_workers=1) as reader:
    next_page = reader.submit(next, pages, None)
    while True:
        page = next_page.result()  # Oracle errors propagate here
        if page is None:          # An empty page is not the end
            break
        next_page = reader.submit(next, pages, None)

        lift_pairs = target.lookup_pairs(keys_from(page), cutoff)
        additions, warnings = compare_page(page, lift_pairs)
        store.save_upsert_page(run, additions, warnings)

store.finish_preparation(run)     # prepared totals; delete_count = 0
# Apply later fetches payloads for addition_diff only.

Recommended implementation steps

  1. First, change the data flow: page lookup → compare → save differences. Disable deletion calls. Check this sequentially before adding threading.
  2. Then overlap the reads: add exactly one next-page future. The page comparison and SQLite writes remain sequential.
  3. Update the examples and regression tests: missing/equal/older/newer pairs, multiple and empty pages, reader errors, replay, and proof that deletion is never called.

Details to agree: keep the inclusive source and LIFT cutoff as before. A LIFT row beyond the cutoff can still appear missing during prepare; apply’s existing newer-date check leaves it alone. Validate NULL/duplicate values on source and matched LIFT keys; unrelated LIFT rows are no longer scanned. Preparation is finished only after every page succeeds.

Up to two source pages plus the current lookup/diff data are held locally. Source scanning/sorting and total key/date traffic remain; prefetch helps when Oracle fetch time can overlap LIFT comparison time. A target key index matters for the page lookups.
