2. New work — in five small parts

  1. Inspect EV data. Find final values, intermediate fields, model versions and parcel structure for the chosen date. This determines the exact schema and translation rules.
  2. Fix the data model. In Lift, change pripis_vmxpd_x_enote.vrednost_izr from Integer to Decimal Number. In PostgreSQL, use numeric; numeric(20,2) is suggested. Add the comparison tables.
  3. Compare final answers. Match building parts by date + ID + model + version. For parcels, sum each source by date + parcel + model + version before joining. Different pizza slices must still be compared as whole pizzas. Save calculated and generalized rounded comparisons separately; delta always means ISAM − EV.
  4. Explain calculated differences. When both sources exist and abs(delta_izr) exceeds tolerance, translate EV ingredients into ISAM meaning and compare them. Preserve the original field and rule. Mark untranslated or ambiguous components visibly. Rounded-only differences normally do not trigger this step.
  5. Add the comparison button and results view. A third date-row SFC button is a sensible proposal. Start the new workflow, then let users filter saved results and open intermediate details from a difference row.

4. Where are comparison results saved?

New persistent PostgreSQL tables exposed through Lift. Python/SQL fills them; Lift displays them. The ticket explicitly asks for “nove tabele v liftu” and a configuration table for simple mappings. The following names and three-table layout are proposals.

Suggested tableOne row / essential fields
pripis_primerjava_rezultati
The scoreboard		One date + property + model + version. ID, date link, unit type, natural property ID, model/version, ISAM/EV calculated values, delta_izr, status_izr, both rounded values, delta_posplosena, status_posplosena. For parcels: counts and JSON IDs of parts, total area/share when available, and nivo_primerjave = PARCELA_MODEL_AGREGAT.
pripis_primerjava_vmesni
The explanation		One compared ingredient linked to a final-result row. Component key, group (variable/factor/etc.), key, ISAM value, translated EV value, status, original EV field and conversion rule. Exact value types depend on EV analysis.
pripis_primerjava_preslikave
The dictionary		One simple translation rule: model/version, EV field, canonical ISAM component key/group, conversion rule and unit/precision settings where needed. Complex transformations belong in versioned SQL views/functions in the repo.

Final statuses distinguish equal, different, missing ISAM/EV and calculation errors on either side. Parcel intermediate matching uses shared business attributes, not parcel-part IDs or row numbers. If a unique match is impossible, flag NEENOLICNA_STRUKTURA and show an aggregate comparison.
