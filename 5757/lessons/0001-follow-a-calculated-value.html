Where does one ISAM value come from?

5757 asks us to compare ISAM and EV values for the same cutoff date, and explain calculated differences. Before building that comparison, learn to locate its ISAM input.

Your win today: explain how a saved unit value is connected to a date and a model version. We will stop there.

1 · WHEN?

pripis_presecni_datum

A record identifies a cutoff date.

id identifies the record; datum is the actual calendar date. The workflow receives an ID and resolves its date.

Illustration: record D1 → date 2026-06-30. IDs here are teaching labels, not real UUIDs.

↓ linked by id_rel_pr_datum
2 · WHICH MODEL VERSION?

pripis_vm_x_pd

A record selects a model version for that date.

id_rel_pr_datum → the date record.
id_rel_verzije_modeli → a record in md_verzije_modeli, which supplies the model and version.

Illustration: selection S1 → date D1 + model M, version 3. Many selections can belong to a date.

↓ linked by id_rel_vm_pd
3 · WHAT VALUE FOR THIS UNIT?

pripis_vmxpd_x_enote

A record stores a unit’s calculated result under that model/date selection.

id_rel_vm_pd → selection S1.
id_rel_prip_enota → the prepared unit.
vrednost_izr → calculated value before generalized rounding.
vrednost_zaokrozena → generalized rounded value.

It also carries calculation errors and intermediate variables/factors. The unit’s natural property identity comes from its prepared-unit record.

Source: the existing calculation writer, function _zapis_pripis, and model/date selection code. This verifies code relationships, not the current live database schema.

What must change here for 5757?

The ticket requires pripis_vmxpd_x_enote.vrednost_izr to support decimals: Decimal Number in Lift and numeric in PostgreSQL. numeric(20,2) is suggested. Check both layers; changing the type cannot recover decimals already lost.

These existing tables supply ISAM’s answer. The comparison needs new saved results containing both ISAM and EV values, deltas and statuses. We will introduce those after this chain is clear.
