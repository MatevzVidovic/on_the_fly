1. Save the two answers beside each other

The existing pripis_vmxpd_x_enote contains the ISAM result. We need a separate result that says what happened when we compared it with EV.

PROPOSED TABLE · pripis_primerjava_rezultati

One row = one final comparison

Which property?
Unit type + natural ID: building-part ID or parcel ID.
Under which scope?
Cutoff date + model + confirmed corresponding model versions. Preserve both source version identifiers.
Which answers?
ISAM calculated / EV calculated, and ISAM generalized / EV generalized.
What difference?
delta_izr and delta_posplosena, always ISAM − EV.
What happened?
Separate status_izr and status_posplosena: equal, different, missing on either side, or a calculation error on either side.

A run link is also useful to isolate repeated executions. The ticket requires saved comparison tables, but does not prescribe our run/table layout. See sections 2 and 6.

Parcel complication: one result row is not one parcel part

For one date + parcel + model + version, suppose ISAM has parts valued 60 and 40; EV has parts valued 30, 30 and 40.

ISAM: sum its parts → 100 ─┐
                          ├→ final row: delta 0
EV:   sum its parts → 100 ─┘

Joining raw parts first would produce six pairs and duplicate the values. Aggregate each source separately, then join the totals. Keep part counts 2/3, source part IDs, available total area/share and PARCELA_MODEL_AGREGAT.

Generalized parcel totals have an unresolved rule: sum rounded parts, or round the calculated total once. Show both alternatives with labels until agreed; do not silently choose one.

PROPOSED TABLE · pripis_primerjava_vmesni

One row = one compared ingredient

Link it to the final row through a proposed id_rel_rezultat. Store the canonical component key, group (variable, factor, zone, etc.), ISAM value, translated EV value, comparison outcome and translation issues.

Also retain the original EV field(s) and the applied rule. Otherwise a user can see a difference without being able to verify how we produced it.

Illustration: final result R1 → ingredient area_m2 → ISAM 8000, translated EV 8000, source EV area_ha = 0.8, rule × 10000. These field names are teaching examples, not a verified EV mapping.

A numeric ingredient may have a delta; a category or text ingredient may need equality/missing/error comparison instead. Exact value storage types depend on EV analysis. An ingredient difference is evidence, not automatically a proven root cause.

3. Define how EV becomes comparable

We cannot compare EV column names directly with ISAM keys. A translator must turn them into the same meaning: units, precision, NULL semantics, merged/split fields and model-version-specific rules.

PROPOSED TABLE · pripis_primerjava_preslikave

One row = one simple translation rule

Identify the model/version scope, source EV field, target canonical key/group and applicable conversion settings. Keep these definitions separate from the thousands of comparison observations they produce.

Simple mappings belong in this configuration table. Structural transformations belong in versioned SQL views/functions in the repository. Each detail row must identify the rule/version actually used.

For parcel ingredients, define a shared business key per model. If two components remain indistinguishable, report NEENOLICNA_STRUKTURA and aggregate evidence. Do not invent pairs using part IDs, row numbers or equal areas.

Unfinished prerequisite: EV’s id_model_ver has not yet been authoritatively mapped to ISAM’s verzija. Translation rules and version correspondence solve related but different problems: one aligns ingredient meaning; the other establishes which rule sets are comparable.

4. Connect the data model to something runnable

A small Python/SQL workflow can contain the comparison logic. It needs these handoffs:

  1. SFC → coordinator: send the selected date-row ID. Resolve the actual date, fix settings and check the upstream ISAM calculation is ready.
  2. Reader → comparator: supply dated source values, natural property identities, model/version evidence and calculation errors. Filter by date early.
  3. Comparator → explainer: compare final values in SQL, aggregating parcels first; retain unmatched rows. Pass only eligible calculated differences to the explainer.
  4. Explainer → store: translate EV ingredients and compare them; preserve provenance, untranslated fields and ambiguities.
  5. Store → Lift: save linked final/detail rows. Let users filter by deltas, model, statuses and property ID, then open translated evidence from a calculated-difference row.

Use indexes appropriate to the date/matching queries and bulk SQL operations; avoid pulling every date and every intermediate value into Python. Read result pages rather than loading the whole comparison into the screen.

A practical run record and failure contract (proposed)

A small run record can store date, settings, rule versions and running/failed/completed state. Link output rows to it. Retries should replace/resume a run safely or produce a separate isolated run, without duplicate rows or mixed attempts.

Publish a completed result only after its required final and detail writes succeed. The coordinator handles execution; storage handles persistence; Lift shows the state. This is our proposed reliability design, not an extra service or a mandated ticket table.
