5757 · PROPOSED MODULE RESPONSIBILITIES

Same date. Comparable answers. Traceable differences.

Compare ISAM and EV property values for one cutoff date. Keep calculated and generalized values separate, then explain calculated differences using intermediate data with the same meaning.

1 Start→2 Read→3 Compare totals→4 Explain eligible differences→5 Save→6 Show
01 · RUN COORDINATOR

Own the comparison run

Turn a selected date into one controlled, repeatable comparison.

Receives → returnsDate-row ID + tolerance → run ID + progress / outcome
Handles in the background
  • Resolve the actual date and freeze the run settings, including translation-rule versions.
  • Check that ISAM preparation and calculation are ready; stop with a clear reason if inputs are unavailable.
  • Call roles 2–5 in order; track failure, retries and completion. Prevent conflicting runs for the same scope.
02 · SOURCE READER

Supply dated evidence

Deliver ISAM and EV records that actually belong to the requested date.

Receives → returnsRun context → dated values, identities, source errors + intermediate-data access
Handles in the background
  • Resolve source tables, date semantics, property IDs, models and versions. Filter by date before large joins.
  • Preserve decimal values, NULLs, missing records and calculation errors as distinct evidence.
  • Return source references; read intermediate data only for candidates selected by role 3.
03 · FINAL-VALUE COMPARATOR

Decide which answers differ

Produce one fair comparison per property, model and version.

Receives → returnsDated evidence + tolerance → final rows + explanation candidates
Handles in the background
  • Match building parts by date + building-part ID + model + version. Detect duplicate keys.
  • Aggregate parcel parts separately on each side by date + parcel + model + version before joining; retain counts, IDs and available area/share.
  • Keep unmatched records; calculate deltas as ISAM − EV and separate calculated/generalized statuses.
  • Select explanation candidates only when both sources have valid calculated values and abs(delta_izr) > tolerance. Generalized-only differences stay in final results.
04 · INTERMEDIATE EXPLAINER

Compare meaning, not field names

Expose which ingredients differ without inventing matches.

Receives → returnsEligible final rows + source details → canonical comparisons + translation issues
Handles in the background
  • Translate EV into canonical ISAM components using model/version rules: rename, merge, split, units, precision and NULL semantics.
  • Match parcel components by shared business attributes defined per model; never by part ID or row number.
  • Keep original EV fields and applied rules. Surface untranslated data and NEENOLICNA_STRUKTURA; use aggregate evidence when unique matching is impossible.
  • Show component differences as evidence; do not claim an automatically proven root cause.
05 · RESULT STORE

Publish a trustworthy result

Make a completed comparison durable and queryable in Lift.

Receives → returnsRun + final rows + detail rows → persisted, linked result set
Handles in the background
  • Own the proposed run, final-result and intermediate-result tables; link details to their final row.
  • Use run-scoped writes and a completion marker so partial output is never shown as a completed run. Make retries avoid duplicate results.
  • Provide indexed, paginated reads by run/date, property, model, statuses and deltas. Retain diagnostics for failed runs.
06 · LIFT INTERFACE

Let the user run and inspect

Expose the comparison and its evidence through a simple screen.

Receives → returnsUser selection + saved results → start request, filtered rows + detail view
Handles in the background
  • A date-row SFC starts the coordinator with the date ID; show the returned run state.
  • Display both values, both deltas and both statuses, date, identity, model/version and parcel counts.
  • Filter persisted results and open intermediate evidence from an eligible calculated-difference row.
  • Explain missing, failed, ambiguous and untranslated cases visibly; all comparison logic stays in roles 3–4.
07 · SHARED RULES & DATA CONTRACT

Define what “comparable” means

Supplies roles 1–4: validated tolerance, model/version mappings, component keys, units, precision and rounding policy. Keep simple EV mappings in a configuration table and structural conversions in versioned SQL. Reject missing required rules or record an explicit issue.

Owns the schema prerequisite: pripis_vmxpd_x_enote.vrednost_izr must be Decimal Number in Lift and numeric in PostgreSQL; numeric(20,2) is suggested, pending precision confirmation. Schema changes happen during setup, not each comparison run.

How these roles reach the goal

Reader guarantees the date and provenance → comparator guarantees fair totals → explainer guarantees semantic evidence → store guarantees durable results → Lift makes them inspectable. The coordinator joins these steps under one run; shared rules keep their assumptions consistent.

These are responsibilities, not seven separate deployments. A single Python/SQL workflow can implement roles 1–5, with SQL doing the bulk work and SFC handling role 6.

Decisions still needed

Analyse EV to confirm source fields, historical-date access, model/version correspondence and parcel component keys. Agree tolerance and parcel rounding: sum rounded parts or round the total once. Until agreed, show both rounding alternatives and label them explicitly.

Preparation and ISAM calculation are upstream prerequisites. This design consumes their results; it does not redefine their responsibilities.
