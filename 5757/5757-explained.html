TASK 5757 · SIMPLE EXPLANATION

Compare two answers.
Explain why they differ.

ISAM and EV both put a value on a property. Your job is to put their answers side by side for the same date. If the answers differ, compare the ingredients used to make them.

Existing ISAM + EV data → new comparison workflow → new result tables → Lift screen

The task in 5 sensible parts

1. Look at the ingredients

EV data + existing ISAM code — Find the EV final values and intermediate fields. Check how dates, model versions and parcel pieces are recorded. This decides the exact table fields and translation rules.

2. Make the storage boxes

Lift + PostgreSQL — Change pripis_vmxpd_x_enote.vrednost_izr to Decimal Number in Lift and numeric in PostgreSQL (numeric(20,2) is suggested). Add tables for comparison results and simple EV-to-ISAM mapping rules.

3. Compare the final answers

lift-temporal-python · Python + SQL — Read both sources for one selected date. Compare the calculated value and generalized rounded value separately. Save both numbers, ISAM − EV, and statuses for equal, different, missing or failed calculations.

Building parts: match ID + model + version + date. Parcels: first sum each side by parcel + model + version + date, then compare those totals. Like comparing two whole pizzas even if they were cut into different slices.

4. Explain the differences

Same workflow + mapping rules — Only when both sides exist and the calculated difference exceeds the tolerance, translate EV ingredients into ISAM names/meaning and compare them. Keep the original EV field and translation rule. Mark missing translations and ambiguous parcel matches visibly. A rounded-only difference does not normally trigger this step.

5. Add the button and results screen

Lift SFC + table/view configuration — Select a date and start the workflow. Show saved results with filters for differences, status, model and property ID. Clicking a difference opens its ingredient comparison.

Where are the results written?

Into new persistent PostgreSQL tables registered in the Lift data model for pripis. Python/SQL fills them; Lift reads and displays them. They are separate from the existing calculated-value source table.

A small proposed design — these names are suggestions, not specified by the task:

  • pripis_primerjava_rezultati: one final comparison per date, property, model and version; both values, both deltas/statuses, parcel counts and source-piece IDs.
  • pripis_primerjava_vmesni: ingredient comparisons linked to a final-result row, with translated values and their origin/rule.
  • pripis_primerjava_preslikave: simple translation rules by model/version. Complex translations stay in versioned SQL views/functions in the workflow repo.

The task does not name the database/schema, table names or exact Lift configuration location. Confirm the GURS pripis connection and inspect EV data before fixing the schema. A workflow return value can report completion; the large result set belongs in these tables.

How does this interact with old ISAM code?

It consumes its outputs: pripis_vm_x_pd and pripis_vmxpd_x_enote. Existing preparation lives in isam/pripis/; calculation lives in isam/modeliranje/izracun_vrednosti/.

Related code already exists in Temporal: _gurs/priprava_prepisa/, _gurs/modeling/ and _gurs/modeling_values/. Both checked calculation writers already emit round(b.vrednost_desna, 2)::numeric. Check the actual column type: a numeric SQL expression alone does not fix an integer column or recover previously lost decimals.

Start with a new comparison workflow, using existing outputs. Change existing calculation code only if analysis shows a needed value is missing or incorrect. Which repo runs the current calculation must be checked in the deployed setup.

Decisions still needed

Confirm EV intermediate fields, how parcel ingredients match, the tolerance, and whether to sum rounded parcel-piece values or round the total once. Until rounding is agreed, show both methods. For large data, filter by date early, aggregate in SQL and index matching keys.
