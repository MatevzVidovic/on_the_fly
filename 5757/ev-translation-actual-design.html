The EV translation layer

Its job: turn EV intermediate results into records that have the same meaning as ISAM’s intermediate results. The comparison code can then compare those records without knowing EV’s original layout.

Source tables and formats below were inspected in the database/code. New table names and record layouts are proposals. Specific business mappings are not yet approved.

1. Start with a final-value difference

The final-value comparison has already identified a property, cutoff date and corresponding model versions. Intermediate work runs only when both calculated values are usable and abs(delta_izr) > tolerance.

For those selected properties, read:

ISAMpripis_vmxpd_x_enotespremenljivke_vrednosti and faktorji_vrednosti, plus the correct model-version key lists.

The EV historical tables are candidates, not a completed extraction design. We still need to confirm how their rows relate to the final-value rows, the selected date, model version and parcel structure.

ISAM also needs preparation. Its saved intermediate values are ordered lists. The model’s ordered key lists tell us which value means what. We must validate that context and list lengths before pairing keys with values. In the inspected small sample, the referenced model record was missing. Those records cannot be decoded safely until that is resolved.

2. Store simple mapping rules in one table

PROPOSED · pripis_primerjava_preslikave

One row defines one simple translation

Rule informationPurpose
Rule ID and revisionIdentify the exact rule used in a result.
Unit type, model and confirmed version correspondenceSelect a rule only where its meaning is valid. EV and ISAM version numbers need not be identical.
EV source fieldIdentify what to read from an allowed source.
ISAM target key and groupSay which variable, factor, level, zone or other ingredient it represents.
Conversion settingsDeclare value type, units, precision and NULL handling. Use a small set of supported operations such as identity or scaling.

Candidate example: EV has f_bon, and inspected ISAM KME model definitions also list f_bon as a factor. A rule could map EV f_bon to ISAM FAKTOR / f_bon unchanged—after confirming they have the same meaning for the corresponding versions. A matching name alone is not enough.

If a transformation combines fields, splits a record or regroups parcel data, implement it as a versioned SQL view or function. Keep simple settings in the table and structural logic in reviewed SQL; do not turn the mapping table into a place for arbitrary SQL expressions.

3. Return a common record format

Normalize ISAM’s ingredients and translate EV’s ingredients into the same format. These can be temporary SQL results inside the workflow; a separate permanent canonical-data table is not required.

property/date/model context
part or component identity, where relevant
group                  e.g. FAKTOR
key                    e.g. f_bon
value                  e.g. 1.00
value type / unit      e.g. decimal / dimensionless
source reference       table + record + original field/value
translation reference  rule ID + revision
translation outcome    usable / untranslated / ambiguous / invalid

The context links to the final comparison and preserves both original model-version identifiers. A component identity distinguishes multiple ingredients with the same key on a parcel; it must come from confirmed shared business attributes.

Keep decimal values exact. Preserve the difference between an absent field, NULL, empty text and zero unless an explicit business rule equates them. Failed conversions become visible issues, not fabricated values.

These values are illustrative. The source mapping remains a candidate. A factor difference is evidence, not proof that it caused the final-value difference.

4. Save the comparison and its evidence

PROPOSED · pripis_primerjava_vmesni

One row records one ingredient comparison

Store the final-result link, canonical identity/group/key, both values, comparison outcome, translation issues, original EV field/value and applied rule revision.

Use numeric deltas for numeric values; compare text/categories according to their declared meaning. Keep one-sided or untranslated ingredients visible instead of using an inner join that drops them.

Lift opens these detail rows from the final comparison. A user should be able to answer: “What differed, where did this EV value come from, and how was it translated?”

Parcel matching needs its own check

The final parcel total is compared after separately aggregating each source. That does not establish how the individual ingredients match.

For detail comparison, check a model-specific key made from shared business attributes. If that key is not unique, mark NEENOLICNA_STRUKTURA. Keep the final aggregate comparison and show aggregate ingredient evidence only where that aggregation is meaningful. Do not pair parts by IDs, row order or area alone.

How this fits into the workflow

Eligible final-comparison rows
    ↓
Read only their dated ISAM and EV ingredients
    ↓
Resolve keys, version context and component identities
    ↓
Apply mapping-table rules and versioned SQL recipes
    ↓
Compare common records, retaining issues and unmatched data
    ↓
Save linked detail rows → display in Lift

This can live in one comparison workflow, with SQL doing bulk work and Python coordinating it. It does not require a separate deployed service.

First implementation target: one model, confirmed version correspondence, and a reliably matched property. Prove that the source selection, translation and saved evidence are correct before extending the rules to more models and parcel structures.

Three different things: a mapping row defines a rule; a common record is that rule’s output; a detail row records the comparison with ISAM.
