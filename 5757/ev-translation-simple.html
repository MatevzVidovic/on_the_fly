5757 · THE TRANSLATOR · A TWO-MINUTE EXPLANATION

Make two ingredient lists speak the same language

ISAM and EV calculated different property values. Now we want to compare the ingredients they used: areas, factors, zones and other intermediate results.

But first, we must make those ingredients mean the same thing.

Like comparing two cake recipes

One cook writes 0.8 kilograms of flour. The other writes 800 grams.

The numbers look different. The amount is the same. A translator converts them into the same unit before we compare.

For property data, it looks like this

EV’S INGREDIENT

Area: 0.8 hectares

EV has its own field names and way of storing information.

↓ Our rule: multiply hectares by 10,000
COMMON WORKSHEET

Area: 8,000 square metres

This agreed format is what the ticket calls “canonical ISAM structure.”

↓ Compare with the equivalent ISAM ingredient
SAVED COMPARISON

ISAM: 8,000 · EV: 8,000 → equal

Keep the original EV value and the rule, so we can explain where the answer came from.

Invented example for teaching. The actual EV fields, units and mappings must be confirmed.

We need three small things

1 · A DICTIONARY TABLE

“This EV field means this ISAM ingredient.”

Store simple renaming and conversion rules, scoped to the right model/version. For example: hectares → square metres.

2 · SQL RECIPES

“This conversion needs a few steps.”

Sometimes two EV fields make one ingredient, or parcel parts need regrouping. Write those more complicated rules in versioned SQL files.

We can split data only when the source contains enough information to do it correctly.

3 · A DETAIL-RESULT TABLE

“Here is what we compared.”

Each row records which property/date/model, which ingredient, both values, the outcome, and the source/rule used. It links back to the final-value comparison.

The translator does not recalculate EV’s property value. It reshapes EV’s existing intermediate evidence so we can compare it with ISAM’s evidence.

When we cannot translate safely

Missing does not automatically mean zero. Unknown fields stay visibly untranslated. Parcel parts that cannot be matched uniquely stay visibly ambiguous—we keep the parcel-total comparison and avoid invented pairings.

ISAM also needs readable ingredient labels: its saved values are currently ordered lists. We must recover the correct matching keys before comparing them.

Run this detail work only when both calculated values are usable and their absolute difference exceeds the configured tolerance. First make it work for one model and one reliably matched property.
