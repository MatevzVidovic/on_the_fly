01 / YOUR WAL QUESTION

“A separate history of everything that changed?”

Broadly, yes: a separate ordered recovery stream on disk. Records describe storage operations on pages, tuples and indexes; some contain whole-page images. They carry enough information to redo those operations. WAL positions are called LSNs.

It is not a per-table, human-readable audit trail of every SQL statement and its timestamp. Records from different tables and transactions share the stream, and old WAL is eventually recycled or removed.

02 / YOUR COMMIT QUESTION

“How does it know what changed at the end?”

It recorded the changes while executing each statement. Row headers identify the transaction that created or replaced a version. WAL records were generated along the way.

COMMIT records the outcome and, with the assumed settings, waits for the commit WAL record to be durable. It does not compare before/after tables, walk every changed row to publish it, or copy a private transaction-sized dataset into the table. Outcome bits are cached and tracked in pg_xact; recovery can restore them from durable WAL.

03 / YOUR UNFINISHED TRANSACTION QUESTION

“Where are its changes stored meanwhile?”

In new row versions in normal table pages, initially modified in shared buffers. An UPDATE also records the replacing XID on the old version. Those pages can be flushed to disk before commit, provided the corresponding WAL is durable first.

Other readers can encounter those bytes in memory or on disk. MVCC uses their snapshot, transaction status and row headers to ignore versions they cannot see. Ordinary SELECT does not replay WAL to reconstruct an older row.

04 / YOUR ROLLBACK QUESTION

“Does rollback write every old value back?”

For this ordinary UPDATE, no reverse UPDATE is needed. After T42 aborts, versions it created are invisible. Its attempted replacement of the old row has no effect on visibility, so the original committed version remains readable.

Physical garbage can remain until pruning or vacuum reclaims it. Rollback does not unwind the WAL stream or instantly shrink files; it also does not undo work committed by an earlier transaction.

Crash recovery: REDO storage safely

Start from the recovery checkpoint and replay valid durable WAL as needed. A page’s LSN helps determine which changes it already has. Restore transaction outcomes too: a transaction without a durable commit is not treated as committed. Even if its tuple bytes are reconstructed, those tuples remain invisible.

MVCC: select the visible version

The writer sees its own completed statements. At Read Committed, each new ordinary SELECT gets a new snapshot. At Repeatable Read, an established snapshot can keep seeing the old version after another transaction commits. An UPDATE or SELECT FOR UPDATE can wait on the writer instead of behaving like these plain reads.

Why our failed backfill still filled storage

Millions of UPDATEs→New tuple + index versions+WAL produced before COMMIT→Barman falls behind

Aborting the transaction stopped its changes from becoming visible. It did not erase the already-written tuples or WAL. Barman’s physical stream can receive that WAL before commit; it must preserve physical recovery information even for work that later aborts.

Two different cleanup jobs: pruning/vacuum makes dead-row space reusable in tables. WAL recycling/removal depends on checkpoint progress, backup/replication consumers and retention settings. A shrinking slot backlog is not a direct measurement of filesystem space returned.

The header numbers are not the entire visibility algorithm

xmin and xmax are transaction IDs, not timestamps. PostgreSQL also consults snapshots, active-transaction information, transaction status and hint bits; command IDs distinguish successive statements inside the same transaction. An xmax value does not alone prove a row was deleted: its transaction may have aborted, and locks/MultiXacts use these fields too. Here the IDs show only one simple UPDATE chain.

Does the whole transaction stay in memory until COMMIT?

No. Both table-page buffers and WAL buffers are reused while the transaction is running. PostgreSQL flushes them as necessary, respecting WAL-before-data ordering. A huge transaction can generate huge disk usage without keeping every changed row or WAL record in RAM. Sort/hash operations, locks and other transaction resources can still consume memory.

What if it crashes before the abort record is flushed?

For the ordinary transactions shown here, recovery does not require a durable ABORT record to keep uncommitted work invisible. A transaction lacking a valid durable COMMIT is not committed. Conversely, after a normal durable COMMIT, recovery must preserve the committed result even if cached pages were lost. This is why we separate physical recovery from row visibility.
