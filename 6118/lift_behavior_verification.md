## Conclusions

- Editing SQL or field mappings does not explicitly clear the watermark or delete target rows. Integration update delegates its payload directly to the update command ([update facade](../fmp/app/_AttributeTables/Services/Facade/AttributeTableIntegration/UpdateAttributeTableIntegrationFacadeService.php#L54)). Field save creates/updates individual mappings; it does not reset integration timestamps ([field save](../fmp/app/_AttributeTables/Services/Facade/AttributeFieldIntegration/SaveAttributeFieldIntegrationFacadeService.php#L127)).
- Preserve `is_full_sync=false`, non-null `last_sync_start`, and `use_changed_datetime_for_delta=true`. SQL switches to full mode if `last_sync_start` is empty, `is_full_sync=true`, or an existing full-sync retry heartbeat is supplied ([mode selection](../fmp/app/_AttributeTables/Services/Facade/AttributeTableIntegration/Processing/ProcessSqlIntegrationTypeFacadeService.php#L57)). **API save defaults omitted `is_full_sync` to true and omitted `use_changed_datetime_for_delta` to false**, so send both explicitly ([request](../fmp/app/_AttributeTables/Http/Requests/AttributeTableIntegration/AttributeTableIntegrationUpdateRequest.php#L90)).
- Exactly one `api_last_sync_field=true` mapping should identify the new `date_change_utc`. Retain the old `date_change` mapping as an ordinary field and retain the exact existing unique ID mapping. Saving fields defaults omitted `x-id` and `x-last-sync-field` flags to false; preserve all existing mapping flags deliberately ([field save](../fmp/app/_AttributeTables/Services/Facade/AttributeFieldIntegration/SaveAttributeFieldIntegrationFacadeService.php#L156)).
- The target datetime field is a native `timestamp`, without an embedded timezone ([definition](../fmp/app/_AttributeTables/Definitions/AttributeField/DateTimeAttributeFieldDefinition.php#L27)). Populate its wall-clock values with UTC. Creating a field alone does not backfill it.

The existing-integration editor saves integration metadata and exits; it does not automatically rebuild field mappings ([editor](../fmp/resources/assets/vue/tools/admin/attribute-table-editor/components/integrations/IntegrationEditor.vue#L144)). The separate mapping editor loads current mappings and remote schema independently ([mapping editor](../fmp/resources/assets/vue/tools/admin/attribute-table-editor/forms/integrations/IntegrationFieldsEditor.vue#L124)). Re-read the persisted ID/date flags after saving.

## Prefer an explicitly timezone-aware Oracle result

```sql
(FROM_TZ(CAST(COALESCE(RT.CREATED, RF.CREATED) AS TIMESTAMP),
         'Europe/Ljubljana') AT TIME ZONE 'UTC') AS date_change_utc
```

`SYS_EXTRACT_UTC(...)` computes UTC correctly, but returns a timezone-less `TIMESTAMP`. In this Lift code, Oracle delta bounds are explicitly `TO_TIMESTAMP_TZ(...)` ([Oracle manager](../fmp/app/_AttributeTables/Services/Util/Sql/Manager/OracleSqlManagerService.php#L115)). Comparing a timezone-less Oracle timestamp to those bounds invokes the Oracle session timezone. Lift's default session initialization sets only NLS formats, **not** `TIME_ZONE` ([initialization](../fmp/app/_Util/Constants/SqlConstants.php#L10), [connection](../fmp/app/_Util/Services/Pool/RemoteSqlConnectionPool.php#L48)). A bare `SYS_EXTRACT_UTC` result therefore adds an avoidable session dependency. `AT TIME ZONE 'UTC'` retains the timezone and formats as UTC with the configured offset-bearing NLS format. Alternatively, wrap extraction with `FROM_TZ(SYS_EXTRACT_UTC(...), 'UTC')`.

Do not rely only on integration `initial_queries` to set the timezone: the count query does not receive those options while paginated fetches do ([delta count/fetch](../fmp/app/_AttributeTables/Services/Facade/AttributeTableIntegration/Processing/Sql/ProcessSqlDeltaIntegrationFacadeService.php#L161)). Fetching uses PDO string results without a timestamp conversion ([remote query](../fmp/app/_Util/Services/Query/FetchRemoteSqlQueryService.php#L93)). Verify an actual preview contains a `+00:00` offset and a known sample matches the PostgreSQL backfill.

## Watermark and replay behavior

- SQL delta uses inclusive `>= minimum` and `<= run maximum`, with the new mapping's **remote alias** as the filter column. If `use_changed_datetime_for_delta=true` and a watermark exists, it is the minimum; otherwise Lift falls back to `last_sync_start` ([delta](../fmp/app/_AttributeTables/Services/Facade/AttributeTableIntegration/Processing/Sql/ProcessSqlDeltaIntegrationFacadeService.php#L127)). PHP datetime formatting uses an explicit offset (`Y-m-d H:i:s.uP`); an offset-less stored watermark uses the PHP app timezone, default UTC but environment-overridable ([constant](../fmp/app/_AttributeTables/Constants/AttributeTableIntegrationConstants.php#L33), [config](../fmp/config/app.php#L83)). Confirm deployed `APP_TIMEZONE=UTC` before interpreting a UTC-naive watermark.
- The watermark becomes the maximum source change timestamp processed, not the last page/key. It is persisted after successful processing; an empty run returns null, and `isset` prevents overwriting the existing watermark ([maximum](../fmp/app/_AttributeTables/Services/Facade/AttributeTableIntegration/Processing/Core/ProcessAbstractIntegrationFacadeService.php#L420), [persistence](../fmp/app/_AttributeTables/Services/Facade/AttributeTableIntegration/ProcessAttributeTableIntegrationFacadeService.php#L141)). Delta row processing is transactional ([transaction](../fmp/app/_AttributeTables/Services/Facade/AttributeTableIntegration/Processing/ProcessSqlIntegrationTypeFacadeService.php#L76)); status/final metadata are outside that transaction.
- Convert the old Ljubljana wall-clock watermark to UTC first, then subtract the desired replay overlap. For 2026-10-12 23:59:59.999 local, UTC is 21:59:59.999, and a further three-hour overlap gives **2026-10-12 18:59:59.999**. Backfill target values does not itself advance the integration watermark.
- Existing rows are UPSERTed using the existing integration ID mapping; existing target UUIDs and created metadata are preserved ([payload](../fmp/app/_AttributeTables/Services/Facade/AttributeTableIntegration/Processing/Core/ProcessIntegrationPayloadFacadeService.php#L228), [upsert](../fmp/app/_Util/Managers/BaseModelManager.php#L71)). This implementation is SELECT-then-INSERT, so avoid concurrent runs; it is not by itself a uniqueness guarantee. Replayed rows can get updated audit timestamps and invoke configured events.
- Delta does not bulk-delete target rows. The supplied query has no `__OPERATION`, so payloads default to UPSERT. Rows excluded by `jn_status <> 'X'` are not deleted from the target by this replay.

## Operational boundaries

Execute the prepared write scripts through an appropriately authorized account. No write was attempted; a non-executing `EXPLAIN UPDATE` was rejected for missing privileges.

Stop concurrent/manual/external runs, and allow any in-flight run to finish before migrating. The ordinary update facade rejects processing-locked statuses. This integration reportedly has `sync_schedule='none'` and `scheduled_task_id=NULL`; verify externally triggered jobs separately. Do not reuse an in-flight workflow retry.

A recent rewind prevents the transition from skipping a recent window; it does **not** prove historical completeness. To repair previously missed rows, replay from before the earliest possible omission while keeping delta mode and the existing key mapping, or perform a targeted historical reconciliation. A full-sync switch is unnecessary for replay and can invoke the full-sync deletion path.
