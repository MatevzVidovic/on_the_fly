PostgreSQL · a three-minute explanation

Write ahead.
Ahead of what?

Ahead of the durable table-page write. A transaction can be committed while some table pages still exist only in memory.

↳

Save the recovery record before saving the changed data page.After a crash, PostgreSQL replays WAL to reconstruct the database. Barman preserves that same stream for backup recovery.

“Ahead” describes storage ordering

WAL records describe physical changes. They are not a list of SQL statements to execute again.

COMMIT: with normal synchronous commit, PostgreSQL waits for the transaction’s WAL, including its commit record, to be durable. It need not flush every changed table page. Pages can also be written before commit, provided their WAL is durable first.

Rollback uses transaction visibility

PostgreSQL’s WAL primarily supports REDO recovery, physical replication and point-in-time recovery.

The transaction is aborted

No reverse UPDATE is needed. WAL already generated remains part of the recovery stream. Rollback does not erase those files or override Barman’s retention requirements.

SET LOGGED is a new operation happening now

The old UPDATE has finished. The conversion must now make the table’s current contents recoverable.

Already backfilled

Unlogged table has the new values

These data changes bypassed WAL. They are absent from physical replication.

→
ALTER TABLE … SET LOGGED

WAL records the current table contents

PostgreSQL rewrites the table into logged storage. This is the expensive step.

→
Protected new storage

The logged copy is replayable

Its WAL precedes durable writes of the new pages. Barman must receive that WAL.

What gets logged afterward? The data needed to reconstruct the new logged copy, containing the table’s present values. PostgreSQL does not re-run yesterday’s SQL or reconstruct its missing statement history.

WAL has no fixed expiry time

WAL from an UPDATE and WAL from SET LOGGED follow the same retention rules.

Generated

WAL occupies disk space

COMMIT and ROLLBACK do not delete the generated WAL.

→
Retained while needed

The oldest requirement wins

Crash recovery, any replication slot, archiving if enabled, and configured retention can keep old WAL.

→
Eligible at a checkpoint

Recycle or remove old files

Recycling reuses allocated files. Removal returns filesystem space. A reserve remains.

How long? With healthy consumers, requirements advance as WAL is received and checkpoints complete. A stalled slot can retain WAL indefinitely unless capped. Your five-minute checkpoint setting is not a five-minute WAL lifetime; max_wal_size is not a hard disk limit.

Do small commits suffice? Only with enough drain capacity.

Batches create opportunities to pause and throttle. Rapid small commits can still fill the disk. Physical WAL streaming can run before COMMIT. Keep the table logged, monitor every retention requirement and actual disk space, and leave headroom for cleanup and normal traffic. Batching does not promise less total WAL.

01 / PURPOSE

“Is WAL for rollback?”

Its central job is to redo storage changes after a crash. PostgreSQL handles ordinary rollback using aborted transaction status and MVCC row visibility.

02 / COMMIT

“But it already committed?”

A committed unlogged UPDATE has no crash-survival guarantee for that table. PostgreSQL empties unlogged tables after a crash or unclean shutdown.

03 / BARMAN

“Why can’t it just flip a flag?”

The protected storage and WAL stream need a complete starting state. A flag alone would leave backup recovery without the table’s contents.

For our backfill: SET LOGGED can produce a large burst for the whole table. Paced logged batches spread WAL generation over time so Barman can catch up. Neither approach makes WAL permanently “sticky”; consumer progress and retention rules determine when it becomes removable.
