2. Where the error happens

① Oracle / source value14:53:26 +02:00Same instant as 12:53:26 UTC.
② Timezone-less storage14:53:26PostgreSQL discards the offset; it does not convert this value to UTC.
③ UTC worker reads it14:53:26 +00:00Now means 16:53:26 Ljubljana. Cutoff: +2 hours.

In ProcessSqlDeltaIntegrationFacadeService::handle(), FMP uses new DateTime(last_changed_datetime). Without an offset in the string, PHP supplies its default timezone. The resulting value is used in the source filter DATUM_SYS >= cutoff.

Verified: a real PostgreSQL SELECT cast plus FMP’s actual local handle() reproduces +7,200 seconds with a UTC worker. Keeping the offset or converting to UTC before storage both pass. This is not yet proof of every historical deployed worker’s configuration.

3. When does it skip records?

It does not require back-to-back runs. It happens whenever a Ljubljana watermark is read as UTC. In summer the error is two hours; in winter it is normally one hour.

  • Run again immediately: if the shifted cutoff is later than the run’s upper bound, the query returns no rows. It can appear there is nothing new.
  • Run tomorrow or next week: the same incorrect lower bound still excludes the first two hours after the saved watermark. Later rows can import normally.
  • Once the watermark advances: the omitted interval is behind the cutoff. Ordinary delta runs do not repair it unless those source records change again.
With today’s stored watermark, the at-risk source interval is October 1, 14:53:26–16:53:26 Ljubljana (upper endpoint excluded). New keys can be missing; existing keys can retain stale values. The row at the old watermark may already be imported; the shifted query excludes its timestamp too.

The suspected historical intervals contain 101 missing May keys and 16 missing August keys. This does not explain every stale record: key 463 reached a successful run’s audited save path with correct dates.

4. What the integration needs to change

Preserve the instant across save → load → Oracle filter. Use one explicit contract, not the worker’s implicit timezone.

  1. For a UTC-naive storage contract: convert the source watermark to UTC before saving it. Today’s example must be saved as 12:53:26, not 14:53:26.
  2. On reading: explicitly parse that stored watermark as UTC and send a timezone-aware cutoff to Oracle. An alternative is end-to-end timezone-aware storage, but that is a broader change.
  3. Handle existing watermarks separately: KN’s existing Ljubljana values need a deliberate migration/reset under the new contract. Do not blindly subtract two hours from every integration—source conventions and daylight saving differ.
  4. Repair the old gaps: fixing future cutoffs alone will not backfill missed intervals. Reconcile or replay the affected ranges using verified business-key upserts.

No fix or data change has been applied. These are the required behaviors; the production implementation must cover metadata persistence, parsing, other integration types, and daylight-saving tests.
