THE INCIDENT / 01

Small data changes. Large WAL consequences.

Three effects can compound during integration-triggered materialized view refreshes.

01

Row churn

Random UUIDs make otherwise unchanged rows different.

02

Checkpoint pressure

A 1 GiB WAL threshold can trigger frequent checkpoints and repeated full-page images.

03

Receiver gap

WAL is generated faster than the Barman replication slot advances.

Observed burst: 113.81 MiB/s generated → 94.12 MiB/s backlog growth.

Production observations: 28 October 2026. Code and metadata audit: 29 October 2026. PostgreSQL 15.7.

New row versions

UPDATE creates tuple versions. Small logical changes still require physical writes.

Index maintenance

Non-HOT updates can add index entries. HOT needs unchanged indexed columns and room on the original page.

Full-page images

A page’s first change after a checkpoint can log its entire image, repeatedly across checkpoints.

5× is an observation, not a universal multiplier. Unchanged TOAST values can be reused in date-only updates. Cluster-wide WAL can also include other work.

REFRESH MECHANICS / 03

Both modes run the full SELECT.

Regular refresh

Full SELECT ↓
Replacement heap ↓
Swap storage + rebuild indexes

Blocks readers. Rewrites the materialized result even when values are unchanged.

Concurrent refresh

Full SELECT → temporary result ↓
Compare old and new complete rows ↓
DELETE removed/changed + INSERT new/changed

Allows readers. Requires a suitable unique index. Equal rows can stay in place.

Concurrent refresh can save persistent writes only when rows compare equal. It is still a full recomputation.

Temporary result storage is not the same as WAL-logged persistent output. If every row changes, concurrent delete/insert work may be more expensive than a regular replacement.

PRIORITIES / 09
Reduce churn first. Then reduce amplification.
1 · Stabilize IDs
Replace random UUID expressions with stable identities at the result grain. Check references and plan for the initial migration’s WAL.
2 · Avoid repeat refreshes
Coalesce requests for shared MVs across integrations. Sequential work within one workflow does not prevent duplicate work across workflows.
3 · Review checkpoint settings
Size max_wal_size for the workload and available disk. Evaluate FPI compression and CPU cost. Measure requested checkpoints and WAL again.
4 · Budget for the receiver gap
Pace refreshes and monitor slot lag and disk headroom. The repair script’s between-batch guard does not throttle a LIFT MV refresh statement.
Do not disable full_page_writes or archiving to suppress symptoms. Increasing max_wal_size alone does not cap slot-retained WAL or cure a sustained receiver bottleneck.
