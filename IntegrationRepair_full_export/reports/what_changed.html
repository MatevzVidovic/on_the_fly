Integration repair · production changes · 15 October 2026

Fewer database waits.
Better Oracle filters.

The main changes speed up apply: fetching the rows to repair and sending them to LIFT. SQLite still stores the repair plan and progress. The full prepare comparison algorithm stays the same.

Implemented · EV parcela configured

1. Fetch Oracle rows by the original key columns

Before
WHERE TO_CHAR(PC_MID) || '-' ||
      TO_CHAR(JN_REV_NUM) IN (...)

Filter a computed string. An index on the two original columns does not automatically speed up this expression.

Now
WHERE (PC_MID, JN_REV_NUM)
      IN ((:id, :revision), ...)

Split each saved key into correctly typed components and filter the original pair, matching the indexed columns. Keep the existing integration query.

Measured: 1,000 payloads fetched in 0.393 seconds.

The old text-filter probe failed after 10.18 seconds, so there is no exact completed old/new ratio. Other indexed samples varied with connection and access conditions. The database execution plan was unavailable. Configuration lives in oracle_keys.json; all ten supported EV composite keys now have mappings. See the 15 October coverage audit.

Implemented · shared apply path

2. Ask LIFT for existing rows once per page

Before

For every repair row: send a query, wait for its UUID and change date, then repeat.

1,000 keys → 1,000 lookup round trips
Now

Fetch the page's existing UUIDs and dates with one WHERE key = ANY(...) query, then look them up in a Python dictionary.

One page → one lookup query

Measured at 1,000 keys: 43.312s → 0.219s, about 198× faster for this lookup phase.

This queries the remote LIFT table before writes; it is not the SQLite prepare comparison. A unique index made each lookup cheap, but could not remove the old network wait per query.

Implemented · actual write throughput unmeasured

3. Send PostgreSQL writes without waiting after each row

Before

Send one INSERT or UPDATE → wait for its reply → send the next.

Now

Pipeline the page's INSERTs and UPDATEs, check all replies, then commit. Mark SQLite progress only after the PostgreSQL commit succeeds.

These are still individual row statements. The improvement removes repeated client waits; it is not a single bulk upsert.

A read-only proxy with 1,000 SELECTs took 43.312s sequentially versus 0.184s pipelined. This supports the network benefit, but does not measure real writes, constraints, triggers or geometry processing.

The apply sequence now

Read pending SQLite page→Fetch Oracle payloads→Validate saved dates→One LIFT lookup→Pipeline writes + commit→Save SQLite progress

Missing or changed Oracle rows are warned and skipped. LIFT rows newer than Oracle are also warned and skipped. Committed but unmarked pages can safely replay after interruption.

What stayed the same—and what saves repeated work

SQLite stays. Matched 100,000-row local tests took 0.22s with SQLite, 0.37s with a DuckDB file, and 0.42s with RAM DuckDB plus a saved snapshot. We did not switch storage backends.

Prepare still streams full inventories and compares locally. The candidate SQLite join was slower. Numeric Oracle pagination and DuckDB remain separate experiments.

Resume avoids starting over. Completed source exports and saved page checkpoints can be reused. --only-src isolates Oracle export; it does not reduce the total work of a full run.

Materialized views are left alone. Removing refresh avoids the known completion error; it is not a measured base-table write speedup.

How much faster is the whole repair?

We have strong measurements for the read phases, but no completed new write benchmark. EV parcela's current planning scenario is about 8–13 minutes for prepare + apply, including its 28,621 prepared upserts. That is an estimate using assumed write costs.

All ten composite-key mappings are now checked with small read-only samples, including the enota revision projections. Large-table write forecasts remain estimates until actual applies are measured.
